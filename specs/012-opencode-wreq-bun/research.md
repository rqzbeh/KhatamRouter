# Research & Codebase Inventory: OpenCode Free Tier TLS Client (wreq-js) Native Bun Support

**Branch**: `port/opencode-bun-native`  
**Date**: 2026-10-27  
**Status**: Completed  
**Subject**: Porting upstream `decolua/9router` commit `ce060c79` (OpenCode Free TLS ClientHello) and `1da5b0d7` (deepseek context window cap) to run natively under Bun 1.4.3 via `wreq-js@3.2.0` with strict security hardening, real fail-open behavior, and zero Node fallback baggage.

---

## 1. Executive Summary & Problem Diagnosis

### The Upstream Issue
The OpenCode Free lane (`oc/*`) answers with `429 FreeUsageLimitError` on requests where the client's TLS ClientHello does not match the fingerprint expected by upstream Cloudflare/edge gates. When requests originate from Node.js using standard OpenSSL, the requests are blocked immediately with HTTP 429 even when bodies, tokens, and headers are identical to those generated by the official OpenCode CLI.

Upstream investigation (`decolua/9router` commit `ce060c79`) identified three independent enforcement gates for OpenCode Free tier:
1. **TLS Fingerprint Gate**: Upstream keys on the cipher-list hash in JA4 (cipher hash `5b57614c22b0`). Reordering the 17-cipher BoringSSL list still passes, but omitting any entry fails.
2. **Session Timestamp Gate**: Upstream decodes the session timestamp from `x-opencode-session` and rejects timestamps falling outside the valid free-tier window.
3. **Body Contract Gate**: The request body must include the CLI's `<env>` marker in the system prompt AND declare matching tools (`read`, `shell`).

### User Directive & Non-Negotiable Decisions
- **User Instruction**: *"no you are not allowed to bypass wreq-js. you are supposed to make wreq-js work under bun!"*
- Bypassing, skipping, or mocking out `wreq-js` in production is strictly forbidden.
- The target deployment environment is a VPS running with datacenter IP addresses, where TLS fingerprint enforcement is actively triggered by upstream edge firewalls.
- Port upstream commit `ce060c79` ("restore the free tier with the TLS client Hello it accepts") to run natively under Bun.
- Port upstream commit `1da5b0d7` ("cap oc/deepseek-v4.1-flash-free context window at 330k").
- Reconcile upstream release commit `3a978a63` into `CHANGELOG.md` and `docs/UPSTREAM-PORTS.md`.

## 2. Technical Inventory & Verified Facts on This Host

The orchestrator and prior probes verified the following concrete facts on this Linux WSL2 / Bun 1.4.3 host:

### 2.1 `wreq-js@3.2.0` Package & Runtime Compatibility
- `wreq-js@3.2.0` installs cleanly with `bun add` and executes under Bun 1.4.3 without requiring Node runtime shims.
- In `package.json` for `wreq-js`, the `"exports"` map explicitly declares a `"bun"` condition that maps directly to `dist/wreq-js.cjs`.
- The native binding for Linux x86_64 is packaged in the optional dependency `@wreq-js/binding-linux-x64-gnu`.
- In a standalone test scratchpad (`/tmp/kr/wreqtest`), `import("wreq-js")` succeeded, and `wreq.createSession(...)` successfully initialized an impersonated BoringSSL TLS session.

### 2.2 Verbatim BoringSSL 17-Cipher List
Upstream `open-sse/services/opencodeTlsClient.js` defines a 17-entry BoringSSL cipher suite list:
```text
TLS_AES_128_GCM_SHA256:TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:ECDHE-ECDSA-AES128-SHA:ECDHE-RSA-AES128-SHA:ECDHE-ECDSA-AES256-SHA:ECDHE-RSA-AES256-SHA:AES128-GCM-SHA256:AES256-GCM-SHA384:AES128-SHA:AES256-SHA
```
- **Probe Result**: Testing with a truncated 2-entry cipher list failed with `NO_CIPHER_MATCH`. The full 17-cipher list is required verbatim because upstream calculates the JA4 cipher hash across the entire negotiated cipher suite array.
- A live probe of `https://tls.peet.ws/api/clean` through the initialized `wreq` session produced JA4 fingerprint `t13d1711h2_5b57614c22b0_78e6aca7449b`.
- The cipher hash `5b57614c22b0` matches the ClientHello cipher suite hash emitted by Bun's native BoringSSL fetch (`t13d1713h1_5b57614c22b0_...`).

### 2.3 `session.fetch()` Contract Under Bun
The object returned by `session.fetch(url, options)` implements:
- `res.status`: HTTP status code (number, e.g. 200).
- `res.statusText`: HTTP status text (string, e.g. "OK").
- `res.headers`: Header container with `.forEach((val, key) => ...)` iteration.
- `res.body`: A standard WHATWG `ReadableStream` where `typeof body.getReader === 'function'`.
- `res.text()`: Asynchronous method resolving to body text string.
- Streaming contract: Handing `res.body` directly into `new Response(res.body, { status, statusText, headers })` allows downstream SSE token consumers to stream without intermediate buffering.

## 3. Upstream Defects & Required KhatamRouter Hardening

While upstream commit `ce060c79` proved the TLS fingerprint concept, its implementation suffers from severe architectural and security defects that cannot be adopted verbatim in KhatamRouter:

### Defect 1: Dynamic Child-Process npm Spawning (`lazyRuntime.js`)
- **Upstream Pattern**: Upstream imported `loadRuntimeDep("wreq-js")` from `open-sse/services/lazyRuntime.js`. When `wreq-js` was missing, `lazyRuntime.js` spawned a child process running `npm i --no-save wreq-js` on the fly.
- **KhatamRouter Defect**: Spawning `npm` at runtime introduces an arbitrary package injection vulnerability, violates container immutability, fails in Docker containers where `npm` is omitted, and crashes in Bun-only environments where Node/npm are deprecated.
- **Remediation**: Declare `wreq-js@3.2.0` in `package.json` under `optionalDependencies`. In `open-sse/services/opencodeTlsClient.js`, use a direct dynamic `import("wreq-js")`. Never spawn package managers or external processes at runtime.

### Defect 2: Fake Fail-Open (Upstream Throws `OpencodeTlsUnavailableError`)
- **Upstream Pattern**: Upstream commented that `wreq-js` fails open to native fetch, but line 73 of upstream's `opencodeTlsClient.js` explicitly threw:
  ```javascript
  throw new OpencodeTlsUnavailableError("wreq-js unavailable ... install the optional wreq-js dependency");
  ```
  This immediately aborted the downstream request with an uncaught error.
- **KhatamRouter Remediation**: Implement **REAL fail-open**. If `import("wreq-js")` fails (e.g. on an unsupported architecture or missing optional binary), catch the error, log exactly ONE diagnostic warning (`[OpenCode TLS] wreq-js unavailable; falling back to native Bun fetch`), and fall back to `globalThis.fetch(url, init)`. Because Bun's native fetch already sends BoringSSL cipher hash `5b57614c22b0`, many requests will still succeed. Never terminate or abort a request because the TLS client library is unavailable.

### Defect 3: Host Reconnaissance Leaks in `<env>` Fingerprint
- **Upstream Pattern**: In upstream `open-sse/utils/opencodeFingerprint.js`, the `<env>` marker derived paths dynamically:
  ```javascript
  const ENV_WORKING_DIR = process.cwd();
  const ENV_TMP_DIR = path.join(os.tmpdir(), "opencode");
  const ENV_PLATFORM = process.platform;
  ```
- **KhatamRouter Security Invariant**: As already established in our tree, leaking local host paths, usernames, and OS configurations to third-party providers constitutes host reconnaissance leakage.
- **Remediation**: Maintain KhatamRouter's fixed neutral dummy constants:
  ```javascript
  const ENV_WORKING_DIR = "/home/user/project";
  const ENV_TMP_DIR = "/var/cache/opencode";
  const ENV_PLATFORM = "linux";
  ```
  These constants satisfy the OpenCode free gate without disclosing operator infrastructure.

### Defect 4: Missing Host Scoping on `directFetch` (SSRF Risk)
- **Upstream Pattern**: Upstream blindly executed `options.directFetch(url, options)` in `proxyFetch.js` for any caller that supplied it.
- **KhatamRouter Defense**: Allowing arbitrary callers to supply custom network dispatchers across arbitrary destinations creates an SSRF and transport hijack risk.
- **Remediation**:
  1. `directFetch` in `open-sse/utils/proxyFetch.js` MUST enforce an origin allowlist: it is ONLY invoked if the target URL hostname equals `opencode.ai` or ends with `.opencode.ai`.
  2. For all other destinations, `directFetch` is ignored and normal fetch is used.
  3. `opencodeTlsFetch` in `open-sse/services/opencodeTlsClient.js` additionally validates the target hostname before dispatching through the `wreq` session.

## 4. Transport Wiring & `codexStt.js` Interaction Analysis

### 4.1 BaseExecutor & ProxyAwareFetch Flow
```
OpenCodeExecutor.execute(args)
  │ Passes directFetch: (url, opts) => opencodeTlsFetch(url, opts, { signal })
  ▼
BaseExecutor.execute(args)
  │ Forwards directFetch inside request options
  ▼
proxyAwareFetch(url, options, proxyOptions)
  │
  ├─► [1] Is proxy configured (connectionProxy or envProxy)?
  │         YES ──► Route through ProxyAgent (proxy takes priority; bypasses wreq)
  │
  ├─► [2] Is strictProxy enabled and proxy intended but unresolved?
  │         YES ──► Reject immediately with Error (fail closed)
  │
  ├─► [3] Is directFetch provided AND target host is opencode.ai?
  │         YES ──► Invoke options.directFetch(url, options)
  │
  └─► [4] Default: Invoke globalThis.fetch(url, options)
```

### 4.2 Codex STT `directFetch` Investigation
- In `open-sse/handlers/codexStt.js` (line 95), `transcribeCodex` passes `directFetch: codexHttpFetch` to `proxyAwareFetch`:
  ```javascript
  const response = await proxyAwareFetch(codex.sttConfig.baseUrl, {
    method: "POST", redirect: "error", signal, body,
    strictTls: true, directFetch: codexHttpFetch,
    headers: { ... }
  }, proxyOptions);
  ```
- Target baseUrl: `https://chatgpt.com/backend-api/transcribe`.
- `codexHttpFetch` is an `https.request` wrapper using `node:https`.
- In our current codebase, `proxyFetch.js` did not implement `directFetch`, so `codexHttpFetch` was historically ignored and requests were sent via `originalFetch` (Bun's native `fetch`).
- **Safety Decision**: Target host `chatgpt.com` is NOT `opencode.ai`. Restricting `directFetch` strictly to `opencode.ai` guarantees that `codexHttpFetch` remains ignored. This preserves existing, tested Codex STT behavior under Bun without exposing OpenAI transcription endpoints to untested Node `https.request` socket handling.

## 5. Model Capability & Upstream Port Reconciliations

### 5.1 Porting Commit `1da5b0d7`
- Upstream commit `1da5b0d7` capped `oc/deepseek-v4.1-flash-free` published context window at 330,000 tokens and `maxOutput` at 128,000 tokens.
- **Rationale**: The OpenCode Free backend rejects prompts larger than ~330k tokens (issue `#5097`). Advertising 1,000,000 tokens causes VS Code Copilot and other clients to delay prompt compaction and crash with HTTP 400.
- **Replacement of Prior KhatamRouter Pin**: In Wave 9 / commit `5cd4a756`, KhatamRouter pinned this model to 200,000 / 32,000 as a temporary defense. Per the user's explicit instruction (*"add all commits you skipped"*), we now adopt upstream's `contextWindow: 330000, maxOutput: 128000` pin in `open-sse/providers/capabilities.js`.

### 5.2 Reconciling Commit `3a978a63`
- Upstream release `v0.5.111` release notes documented the OpenCode Free TLS ClientHello fix and the 330k context cap.
- `CHANGELOG.md` will be updated to reflect the Bun-native port of `wreq-js` and the context window adjustment.
- `docs/UPSTREAM-PORTS.md` section "Deliberately Skipped Upstream Commits" will be revised so `ce060c79` and `1da5b0d7` are moved from the skipped list into the ported/hardened matrix with full architectural documentation.
